# M1 Max decode tuning campaign, 2026-11-13

Box: M1 Max 64 GB, macOS 27.0.0. Model: UD-IQ4_XS huihui (`ud-iq4_xs-huihui-metal.gguf`,
64.9 GB: 55.7 GiB experts, 3.23 GiB dense, 0.63 GiB head, 48 blocks). Config: 204800 context,
MTP drafter (`mtp/rt`), `--spec 2`, `--suffix-draft 1`, `--lookup-max-t 12`, `--kv fp16`,
`--expert-cache 1024`, `--mmap-experts`, arena 32 GB.

Every arm runs the engine exactly as the live server does (`gap/tune/sweep.py`, one line each:
same env, same args, one knob changed), 2048-token prompt, 128-192 new tokens, greedy. Two
metrics are read separately because they answer different questions:

- **window ms** — the T=2 decode window's GPU time: the kernel metric, stable to ~1%.
- **tokens per round** — the drafter's acceptance: drifts ±10% between runs of the same flags
  (expert routing/cache), so tok/s alone is not evidence.

Baseline before this campaign: 27.9-28.5 tok/s, window 57.7-60.9 ms.

## What won

### Dense GEMV tile re-sweep (engine change, `metal/src/engine/window.cpp`)

`gemv_parity --one` per shape at 2 tokens — the `--sweep` mode only tries tiles with the base's
lanes-per-row, so the L=4..8 space had never been measured on this GPU. Every pick is bitwise
(no `NOT BITWISE` row).

| shape | type | today | new | us | gain | per window |
|---|---|---|---|---:|---:|---|
| attn_qkv 2560x10240 | Q6_K | 16,2,4,1 | 4,1,4,1 | 100.9 -> 99.6 | +1% | x35 |
| attn_gate 2560x6144 | Q6_K | 16,2,4,1 | 4,1,4,1 | 63.0 -> 59.2 | +6% | x35 |
| attn_q 2560x12288 | Q6_K | 16,2,4,1 | 4,1,4,1 | 120.2 -> 112.1 | +7% | x12 |
| attn_output 6144x2560 | Q6_K | 32,2,4,2 | 16,2,4,1 | 78.3 -> 67.6 | +16% | x12 |
| ssm_out 6144x2560 | Q8_0 | 32,2,4,2 | 8,1,4,1 | 80.6 -> 63.7 | +27% | x36 |
| lm head 2560x248320 | Q6_K | 16,2,4,1 | 8,2,4,1 | 2284 -> 2091 | +9% | x1 |
| shared down 640x2560 | Q8_0 | 8,1,4,1 | 4,1,4,1 | 11.2 -> 10.9 | +3% | x48 |

Engine effect (KPROF, same conditions): window GPU **45.55 -> 40.95 ms (-10.1%)**;
paired arms: window 60.5 -> 56.3 ms, decode 28.4 -> 29.9 tok/s (+5.3% at equal acceptance).

`STRATA_METAL_M1TILES=0` restores the old picks.

## K/V encoding at real depth (16K-token prompt)

| | window ms | decode tok/s | prefill tok/s | resident |
|---|---:|---:|---:|---:|
| `--kv fp16` | 58.2 / 59.5 | 26.9 / 26.0 | 238 / 239 | 54.1 / 50.9 GB |
| `--kv int8` | 62.1 / 65.2 | 24.4 / 24.1 | 268 / 282 | 52.1 GB |

fp16 K/V is **8% faster per decode window** at 16K (direct half loads against codes+scales), 15%
slower on prefill, and costs 2 GB. It buys exactness and decode speed at once: keep it.

## Correctness

`tools/force_check.py`, 1429 tokens over 10 requests, stock (M1TILES=0) twice and candidate once:
event rule PASS (0 vs 0), rate rule INCONCLUSIVE (+0.54 pts, CI -0.86..+1.85). Two stock arms of
the same build differ by 0.25 pts on their own, so this sample cannot resolve the change; the
per-shape harness says every new tile is bitwise.

## Drafters, 3 interleaved pairs (window / tokens per round / tok/s)

| arm | window ms | tpr | tok/s |

DFlash2 wins on acceptance (2.05 against 1.78 tokens a round) and costs the same window,
but its draft round is 7.7 ms against the MTP layer's 2.3 ms, which is more than the extra
tokens are worth: -9.6% tok/s.  MTP spec 2 stays.  An earlier +15% reading for DFlash2 was
an artifact of a low MTP anchor (23.9-24.4 in that group against 29.0-29.4 here).

## Adopted (live, verified 2026-11-13 16:04)

Config unchanged: arena 32, `--kv fp16`, `--expert-cache 1024`, `--spec 2`, `--suffix-draft 1`,
`--lookup-max-t 12`, context 204800.  Only the engine binary changed (the tile picks above).

`serve_huihui.sh restart` -> models loaded, live answer ok; `/v1/models` reports
`n_ctx 204800`; a 420-token completion returns; engine log `resident footprint after the fill:
the process holds 46.6 GB (49.6 GB resident), planned 47.1 GB`; 30% of the RAM free
(macOS file cache included) with the engine serving.

Arena 34 would buy another -3.9% of the window (-4.5% of the decode window's GPU time) for
+2 GB resident; not taken, because the browser headroom matters more than 4%.

## Depth: the window at 32K tokens

One KPROF arm on a 32767-token prompt (`gap/tokens/t32768.txt`), prefill 249.7 tok/s
(131 s, 1 chunk), then the 2-token window:

| | 2K prompt | 32K prompt | delta |
|---|---:|---:|---:|
| window GPU | 40.95 ms | 42.33 ms | +3.4% |
| qsa (attention/indexer) | 1.63 ms (4.0%) | 2.28 ms (5.4%) | +0.65 ms |
| class order | experts, dense, head, ssm_out | same | — |

So depth costs 1.4 ms a window at 32K: attention is not where the time goes, and the tile
re-sweep holds at depth. This answers the handoff's Q5 for 32K (111K still unmeasured).
